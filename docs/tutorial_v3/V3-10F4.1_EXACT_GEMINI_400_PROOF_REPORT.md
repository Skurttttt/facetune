## Exact Gemini Error

| Field | Value |
| --- | --- |
| HTTP status | `400` |
| API `error.code` | **UNKNOWN** |
| API `error.status` | **UNKNOWN** |
| Reason (`error.details[].reason`) | **UNKNOWN** |
| Sanitized message | **UNKNOWN** |

The deployed build reads the Gemini response body **only on the success path**.
The failure path logs one integer and discards the body unread, so the fields
above do not exist anywhere — not in the function logs, not in the Supabase
platform logs, not in the client. They cannot be recovered retrospectively;
they can only be captured on a future request.

The one piece of live evidence gathered (V3-10F4, unauthenticated, no user
data) remains relevant and is why the status alone is not a diagnosis:

```
POST /v1beta/models/gemini-3.6-flash:generateContent   (deliberately invalid key)
HTTP 400
{"error":{"code":400,"message":"API key not valid. Please pass a valid API key.",
  "status":"INVALID_ARGUMENT",
  "details":[{"reason":"API_KEY_INVALID","domain":"googleapis.com"}]}}
```

An unusable API key returns **400**, not 401 or 403. So does an invalid schema,
and so does a billing/region precondition. All three are `400`, two of the
three are even `INVALID_ARGUMENT`, and only `error.status` plus
`details[].reason` separate them.

## Evidence

### What is established

1. The request reaches Gemini and Gemini answers. The failure is at the model
   provider, not in routing, the entry RPC, the session, the migration or the
   geometry mapper.
2. `HTTP 400` is not self-interpreting. Three distinct faults produce it, two
   of them under the same `INVALID_ARGUMENT` status. Verified live.
3. The error body was never captured, and cannot be recovered after the fact.
4. The union `type: ["string","null"]` form is the only construct in
   `TUTORIAL_V3_PLAN_SCHEMA` that no request in this repository has been
   observed to have accepted. `analyze-face`,
   `generate-makeup-recommendation`, `generate-kit-makeup-recommendation` and
   `plan-tutorial-v2` all use `anyOf: [<schema>, {"type":"null"}]` through the
   same model, endpoint, API version and `responseJsonSchema` field. Every
   other construct in the planner schema — `minItems`, `maxItems`,
   `minLength`, `maxLength`, `pattern`, string `enum`,
   `additionalProperties: false` — is individually proven in production here.

### Why 4 is suggestive but not proof

- Google's current structured-output documentation lists `{"type":
  ["string","null"]}` as **supported** for JSON Schema mode. Field reports of
  `400 INVALID_ARGUMENT` for union types concern the older `responseSchema`
  field. The documentation and the field reports disagree, and this project
  uses `responseJsonSchema`.
- The competing candidates are not eliminated:
  - **`API_KEY_INVALID`** — the account was refunded (§18 of the F4 prompt); a
    re-issued key never written back to `supabase secrets` produces exactly
    this signature.
  - **`FAILED_PRECONDITION`** — billing or region state on the project.
  - **Request size** — the canonical preview is inlined as base64 with **no
    size guard** in `plan-tutorial-v3`, where `analyze-face` caps its input at
    10 MB. An oversized preview is also a 400.

Concluding "the union type is the cause" from this would be inference presented
as measurement. The instrumentation below distinguishes all four on the very
next request.

## Error Classification

Implemented in `_shared/gemini_error.ts`, applied by both V3 Gemini clients.
Classification is driven by the response envelope, never by the bare status.

| Condition | Kind | HTTP out | Code | Retryable |
| --- | --- | --- | --- | --- |
| **400** INVALID_ARGUMENT, no credential/precondition marker | `invalid_request` | 500 | `gemini_invalid_request` | **no** |
| **400** + `reason` starting `API_KEY` | `credential` | 500 | `gemini_credential_rejected` | **no** |
| **400** + `UNAUTHENTICATED` / `PERMISSION_DENIED` | `credential` | 500 | `gemini_credential_rejected` | **no** |
| **400** + `FAILED_PRECONDITION` / `BILLING_DISABLED` / `SERVICE_DISABLED` | `precondition` | 500 | `gemini_account_precondition` | **no** |
| **401 / 403** | `credential` | 500 | `gemini_credential_rejected` | **no** |
| **404** | `model_not_found` | 500 | `GEMINI_MODEL_NOT_FOUND` | **no** |
| **429** | `rate_limited` | 503 | `gemini_rate_limited` | yes, bounded |
| **5xx** | `upstream` | 502 | `gemini_upstream_error` | yes, bounded |
| **timeout** (`TimeoutError`) | — | 504 | `gemini_timeout` | yes, bounded |
| network failure | — | 503 | `gemini_network_error` | yes, bounded |

No 400 of any kind is labelled `gemini_upstream_error` any more, and none is
described to the user as temporary. Bound remains 2 attempts with 400 ms linear
backoff; the V3-6R transient 503 is still absorbed by one retry.
