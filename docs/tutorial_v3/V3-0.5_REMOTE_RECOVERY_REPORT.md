A **sixth** V2 migration exists in the stash and is **not applied remotely**.

function that was never deployed.

quota objects — precisely the outcome this phase forbids. It stays in the
stash. Its exact content is recoverable at any time with:


## 4. Live-Schema Corroboration

`supabase db dump` needs Docker, which is not installed, so exact live DDL
could not be read. **Docker was not installed for this phase.** Two read-only
CLI paths supplied live evidence instead.

`npx -y supabase inspect db index-stats --linked` returns live index and
constraint-backed index names. For `tutorial_v2_*` the live set is:

```
tutorial_v2_sessions_pkey                    tutorial_v2_steps_pkey
tutorial_v2_sessions_owner_identity          tutorial_v2_steps_owner_identity
tutorial_v2_sessions_user_created_idx        tutorial_v2_steps_user_created_idx
tutorial_v2_sessions_analysis_idx            tutorial_v2_steps_session_index_idx
tutorial_v2_sessions_canonical_standard_idx  tutorial_v2_steps_session_index_unique
tutorial_v2_sessions_canonical_kit_idx       tutorial_v2_steps_guideline_path_unique
                                             tutorial_v2_steps_result_path_unique
```

**Every one of those 13 live objects is declared by the recovered
`20260826000100`, and the recovered file declares no index that is absent
live.** Combined with `table-stats` confirming both tables exist, this
classifies the migration as **EXACTLY RECOVERED** rather than merely likely.

**Limitation, stated plainly:** column types, `CHECK` bodies, RLS policy
expressions, trigger bodies and `ON DELETE` actions were **not** read back from
the live database — no Docker-free read-only path exposes them. Confidence in
those rests on (a) exact recovered source and (b) the migration being recorded
as successfully applied. That is strong, but it is inference, not a live DDL
diff. If a byte-exact schema diff is ever required, it needs Docker and
explicit authorization.

### `supabase/functions/_shared/ai_quota.ts` — the one edit made

The restored `plan-tutorial-v2/index.ts` calls
`consumeAiQuota(client, "tutorial_v2_plan")`. The local `AiOperation` union
carried only `main`'s five operations, so the restored file would not have
type-checked. The union was extended to the **eight operations that are live in
the database**, with a comment recording why and warning that future migrations
must be a strict superset.

This is not invented content: every added member is verified live. Each
deployed bundle carries its own historical snapshot of this union
(`generate-tutorial-step` has 6, `plan-tutorial-geometry` has 7,
`plan-tutorial-v2` has 6), so no single deployed copy is authoritative — the
database is. Deno is not installed and no task type-checks these files, so this
change is inert at runtime; it exists to keep the restored source honest.
