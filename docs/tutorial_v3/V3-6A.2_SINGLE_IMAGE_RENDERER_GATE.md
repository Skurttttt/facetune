## 1. The hypothesis was PARTLY CONFIRMED — this is the key finding

> Removing the canonical final preview from the renderer call should eliminate
> style-transfer contamination.

**It did.** The V3-6A.1 failure — finished makeup from the target leaking into
categories the step was not teaching — is **gone**:

- Foundation steps no longer arrive wearing eyeshadow, eyeliner and a saturated
  lip. In all three variants the eyes and lips are left alone.
- Blush no longer merges across the nose; the corrected Step Spec plus the
  single-image architecture produced two correctly separated zones every time.
- No output showed makeup belonging to another category.

That is a genuine architectural win and it should be recorded as such.

**But a different, independent failure dominates.** The model recolours the
facial surface it was asked to annotate:

| Variant | Lip Colour | Foundation |
| --- | --- | --- |
| 1 | lips **desaturated** — natural rose washed out | zone tone acceptable, but **blemishes invented** on forehead/cheek/chin |
| 2 | lips **filled solid red** — reads as applied lipstick | zone visibly **lightens the skin** |
| 3 | lips **desaturated** again | zone is an opaque beige mask, **lightening further** |

Variant 3 added an explicit, evidence-written ban ("never fill, tint, lighten,
darken, saturate or desaturate… outline and annotate, never paint"). The model
still paled the lips and still lightened the skin. **The instruction was not
sufficient to stop it.**

A milder version of the same tendency appears everywhere: a soft cheek flush and
slightly warmer lips relative to the original, in categories that never mention
cheeks or lips. With no target image present, that is not transfer — it is a
**generic portrait-beautification prior** the model applies on its own.

## 2. Architecture Tested

```text
FACE ANALYSIS + SELECTED LOOK + PERSISTED RECOMMENDATION + CANONICAL FINAL PREVIEW
                              ↓
                      MASTER TUTORIAL PLANNER          (gemini-3.6-flash)
                              ↓
                  VALIDATED + PERSISTED STEP SPEC
                              ↓
   ORIGINAL SELFIE + MINIMUM SUFFICIENT STEP SPEC + SCOPED FACE ATTRIBUTES
                              ↓
                      SINGLE-IMAGE RENDERER            (gemini-3.1-flash-image)
                              ↓
                     PERSONALIZED GUIDELINE IMAGE
```

**Exactly one image was sent in all 12 calls** (`imagePartCount: 1`, recorded in
metadata for every request). The canonical final preview was never loaded and
is not expressible in the request shape.

The single-image contract was verified **live**, not just in tests:

```
POST … {"prompt":"x","image":{…},"images":[1]}
→ 400 {"error":"invalid_request",
       "detail":"field \"images\" is not accepted: this renderer takes exactly one image"}
```

Also verified live: `401 unauthorized` without the probe token, `400` on a
malformed body.

### Minimum sufficient Step Spec

`selectedStyleCode`, `targetLookCues`, `faceRationale` and `targetRationale`
were **withheld** from every renderer call — naming a look or describing the
finished appearance is style-transfer pressure in text form. Contract tests
assert none of them, nor the string "soft glam", reaches a prompt. They remain
persisted for the planner and UI.

**This withholding appears to have worked.** No output attempted to reproduce a
Soft Glam look.

## 4. Prompt Iterations

| Variant | Change | Effect |
| --- | --- | --- |
| 1 | Renderer framing ("you are not designing makeup"), identity-preservation list, per-category allow/forbid | Blush and Eyeliner pass. Lips desaturated. Foundation invents blemishes. |
| 2 | + diagram-layer reminder ("printed on paper… if anything looks different once marks are removed, the output is wrong") | Lips **regressed** to solid red fill. Foundation **regressed** to lightening the skin. Blush and Eyeliner unaffected. |
| 3 | + explicit no-recolouring ban, written against the observed v1/v2 failures, + geometry precision note | Lips returned to desaturation. Foundation lightened further. Blush and Eyeliner still pass. |

Variant 3's ban was written specifically against what had been observed
("never fill, tint, lighten, darken, saturate or desaturate… Outline and
annotate. Never paint."). It did not work. That is the strongest evidence in
this gate: **the surface-recolouring behaviour is not reachable by prompt
instruction.**

Iteration stopped at 3 as required. No variant 4.

## 5. Security

| Item | State |
| --- | --- |
| `service_role` used | **No** — never read, printed or referenced |
| `supabase secrets set` / `unset` | **Never run** — no shared secret mutated |
| Gemini key | Server-side only; never read, logged or returned |
| Probe authentication | JWT verification **ON** (deployed without `--no-verify-jwt`) using the existing legacy anon JWT, plus an ephemeral token compiled in at deploy time |
| Ephemeral token | Generated locally, never committed, destroyed after the run |
| Deployment scope | Only `tutorial-v3-single-image-guideline-probe`, explicit slug, `--use-api`, never `--prune` |

### Deployment defect found and fixed

The first deploy used `sed` to substitute the token, which replaced **both**
occurrences of the placeholder — the constant *and* the literal inside the
fail-safe guard — turning the guard into `PROBE_TOKEN === PROBE_TOKEN`, always
true. The deployed probe refused every request with `probe_not_configured`,
surfacing as HTTP 503 to the runner. Fixed by changing the guard to a prefix
check (`PROBE_TOKEN.startsWith("__EPHEMERAL")`), which substitution cannot
rewrite. The fix is recorded in the probe source comment so it cannot recur.

### OPEN HIGH-PRIORITY SECURITY ITEM

> **The previously exposed legacy Supabase `service_role` credential remains
> active and must be migrated or revoked separately before production/release.**

Verified again at the start of this phase via non-secret `hash`/`prefix`
metadata: unchanged from the exposed value. Per explicit product decision it was
treated as a non-blocking, separately-tracked remediation for this smoke gate.
It grants full RLS bypass.

**This item is unrelated to the renderer architecture and is not evidence for
or against it.**

## 8. Architecture Conclusion

**Single-image Step-Spec rendering is not production-feasible as it stands —
but it is much closer than the two-image architecture, and the remaining defect
is narrower and better understood.**

What is now established:

1. **Removing the canonical preview works.** Cross-category makeup transfer,
   which failed V3-6A.1 in every variant, did not occur once in twelve images.
2. **Spatial precision is a Step Spec problem, not a model problem.** Blush went
   from 0/3 to 3/3 by stating geometry explicitly — no prompt change achieved
   that in V3-6A.1.
3. **Line-and-path annotation is reliable.** Eyeliner passed 3/3, twice choosing
   a blue that could never be mistaken for makeup.
4. **Region-fill annotation is not reliable.** Whenever the instruction implies
   covering a *surface* — lips, or the whole face — the model recolours that
   surface instead of overlaying it, and it does so in both directions
   (lightening, saturating) regardless of explicit prohibition.

The dividing line is clean: **the model can draw on the face, but cannot
reliably leave a region's colour untouched while marking that region.**

## 9. V3-6B Recommendation

# BLOCKED — DO NOT START V3-6B

Two of four categories fail, and one of them (Lip Colour) fails in all three
variants. Shipping this would give a user on the Lip step a photo of themselves
with their natural lip colour stripped out, or with red lipstick already
applied — the latter being precisely what the tutorial exists to teach them to
do themselves.

Per the phase rules I made no architectural change in response. Options for the
product decision, informed by this evidence:

1. **Composite client-side.** Have the model return only the annotation, or
   composite its overlay onto the untouched original in Flutter, discarding
   whatever it did to the face. Structurally guarantees identity and no
   recolouring. The strongest option, and the evidence points at it: the
   *annotations* are consistently good; only the *base* is corrupted.
2. **Restrict guidelines to line-and-path categories.** Eyeliner, brows and lip
   *outline* work today. Foundation and lip fill do not. A tutorial could show
   diagrams only where they are reliable and use Flutter-rendered text elsewhere.
3. **Try a different image model** against this same gate — the harness is
   reusable and the four Step Specs are fixed.
4. **Accept region-fill imprecision** — not recommended; it breaks the
   no-finished-makeup invariant.

Blush placement precision (zones sitting lower/more medial than specified) is a
separate, smaller Step Spec refinement that applies regardless of which option
is chosen.

**V3-6A.2: FAIL. V3-6B remains blocked.**
